# 弹幕情报 × Polymarket 行情对接路线图

最后更新：2026-08-18

目标：把虎牙弹幕情报（队伍/选手/盘口/局势/集体智慧信号）与 Polymarket 行情
对接，形成"主客观交叉验证 -> 决策辅助 -> 用户确认挂单"的完整链路。

## 阶段总览

```text
阶段 0（已完成）：弹幕抓取 + 情报提炼 + HTML 报告 + 规则沉淀
  -> DANMU_CAPTURE_RULES.md / DANMU_INTEL.md / DANMU_USERS.md / tools/fetch_huya_danmu.py 等
阶段 1（验证中）：行情对接验证
  -> 拉取链路已验证可用（CLOB prices-history 1 分钟粒度 130 点）；
  -> 比赛覆盖检查：LEC 在 Polymarket 无市场（TH vs Navi 无对应事件），
     LCK/LPL/CS2/Dota/Overwatch 等有覆盖；弹幕情报须先做"市场存在性检查"。
  -> 下一步：找一场 Polymarket 覆盖的比赛，同时抓弹幕 + 拉价格，做真对照。
阶段 2：比赛自动映射
  -> 队名词典（TH=Team Heretics、Navi=Natus Vincere 等）+ 时间窗口匹配 Gamma 事件 slug；
  -> 无市场比赛降级为"仅情报沉淀"（不进入对照）。
阶段 3：弹幕信号 × 价格对照
  -> 前提修正（2026-08-18 用户确认）：直播有延迟，价格必然先行，
     弹幕领先性假设不成立、不做"弹幕预测价格"。
     弹幕×价格对照用于：解释/确认价格异动、量化"弹幕共识 vs 市场价格"偏离、
     终局（闭盘）情绪检测——输出对照报告（事件点前后价差 + 弹幕解读）。
阶段 4：集体智慧信号体系
  -> 灰信号（假赛/剧本/卡盘/博彩质疑）聚合为"观众质疑信号"，
     与盘口/价格对照后标注风险等级；仍不作假赛结论（红线）。
阶段 5：决策辅助
  -> 输出"信号 + 依据 + 建议动作"（只给情报与统计，不给自动下单）。
阶段 6：挂单对接
  -> 用户确认后走现有执行链（grid_plan_runner.py）；弹幕只作边际信息，
     不改变止损/止盈纪律；自动挂单必须用户显式开启。
```

## 实施要点

```text
1. 弹幕时间戳（秒级 UTC）与 CLOB 价格（分钟级）对齐，取事件点前后 10-30 分钟窗口。
2. 队名词典先覆盖 LPL/LCK 白名单队伍（config/market_watchlist.json 已登记联赛）。
3. 每次对照报告注明：弹幕量、峰值时刻、价格前后差、观众质疑信号条数。
4. 灰信号处理：聚合计数 + 典型样本 + "观众质疑，非结论"标注；与盘口情绪交叉。
5. 挂单边界：情报层只输出建议，执行层保留用户确认（红线 1/2/6）。
6. 弹幕定位（2026-08-18 确认）：价格先行，弹幕作"解释层 + 微观信息层 + 闭盘情绪层"，
   不追求弹幕预测价格。
```

## 重点分析维度（2026-08-18 用户确认优先级）

```text
1. 闭盘（终局）情绪检测：比赛末段 / 市场临近结算时的弹幕共识
   （如"GG了 / 翻了 / 一波了"风向 + 质疑信号），作为终局风险/确认参考。
2. 集体智慧信号验证闭环：假赛/剧本质疑聚合 -> 时间分布 -> 盘口/价格异常对照
   -> 赛后应验回填（"观众质疑强度"作为风险指标积累样本）。
3. 微观分析：选手状态、队伍打法、BP 评价（价格看不到的信息，喂画像库）。
4. 盘口讨论对照：观众聊让分/人头盘 -> 大众盘口情绪 -> 与 Polymarket 盘口价格对照。
5. 赛区/版本洞察：LEC 放资源保枪、版本中路大核 -> 形态预期与策略路由参考。
6. 情绪突变检测：正负情绪比分钟级翻转 -> 价格拐点确认信号。
```

## 工程优化方向（2026-08-18 用户确认）

```text
- 协议脆弱性：Codex 持续维护（uid 解析、协议升级适配、断线自检告警）。
- 噪音/黑话词表：持续扩充（选手外号、队伍简称、直播间梗、数字黑话）。
- 多源与身份：同场多直播间并行抓取、去重、时间对齐；uid 稳定追踪高价值用户。
- 数据完整性：接受直播窗口不可逆（实时监控即现状），断线漏数据容忍，
  但通过自检告警降低静默丢失风险。
- 合规边界：用户明确不关注，不作约束（对外展示规则另行讨论）。
```
